## 实现要点

1. 方案甲 `exam:<SID>:seq:<i>`：一次只有一条命令在飞，`set()` 返回后才发下一条，不使用 Pipeline / 多线程 / 异步。
2. 方案乙 `exam:<SID>:pipe:<i>`：`pipeline(transaction=False)`，每批最多 `Q=100` 条，`execute()` 收回本批全部回复后才发下一批。
3. 尾批：1404 = 14×100 + 4，第 15 批只发 4 条（i=1401~1404），脚本逐批打印"发送条数 / 收到回复条数"，并单独读回尾批 4 个键核对。
4. 计时口径：`time.perf_counter()`，区间覆盖命令构造、发送和回复接收；方案乙在最后一批 `execute()` 返回后才停止计时。数据完整性核验全部放在计时区间之外。
5. 每个方案使用独立的客户端，并在计时前做一次经过槽路由的预热（写/删一个 warmup 键），避免把集群拓扑发现算进某一方。

## 测量结果（result.txt 摘要）

| 指标 | 程序输出值 |
|---|---|
| 命令总数 | 1404 |
| Pipeline 批次数 | 15 |
| 最后一批数量 | 4 |
| 方案甲耗时(ms) | 358.163 |
| 方案乙耗时(ms) | 45.456 |

数据完整性：两种方式均 1404/1404 个键存在、值全部正确，无缺失、无错值。

## 结论

**方案乙（普通 Pipeline）更快，约为方案甲的 7.9 倍。**

逐条写入时每条命令都要一次完整的客户端—服务端往返，1404 条就是 1404 次等待；Pipeline 把 1404 条压成 15 批，只需付 15 次往返，省下的主要是往返等待与系统调用开销，服务端真正执行的命令数并没有减少。同一台机器上 RTT 只有零点几毫秒，所以绝对耗时都不大，但相对差距仍然明显。

若差异不明显甚至 Pipeline 更慢，可能的原因：本机同机测试 RTT 极短、往返不是瓶颈；集群客户端要按槽把每批拆分到三个主节点分别发送，分组与结果归并的开销抵消部分收益；单线程 Redis 的总计算量不变；单次测量受连接建立、槽缓存刷新、解释器预热等一次性开销干扰。
